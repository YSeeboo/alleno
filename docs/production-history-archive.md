# 电镀／手工历史归档（保留真实账目）

## 本次确认的范围

- 截止时间固定为 **北京时间 2026-10-29 00:00:00，不含当天**。
- `created_at < 截止时间`，且状态为 `pending`（待发出）或 `processing`（进行中）。
- 包括旧的未发出草稿；不包括当天新单、已完成单、已经归档的单。
- 以单据中保存的业务创建日期为准，不以服务器文件日期为准。

归档只增加独立的归档时间、原因、操作人及批次号，不改原状态、实收数量、
手工消耗／退回数量、库存流水、金额或付款状态，不生成虚构的回收单或损耗记录。
归档不代表全部实收，不代表损耗核销或免除应付款。

## 页面行为

- 电镀单、手工单、电镀汇总默认显示正常单据，可切换「历史归档」「全部（含归档）」。
- 归档单不出现在生产看板的待发出／待收回、创建回收单的待收项、手工客户分拣列表。
- 历史详情仍可打开和导出；展示归档原因、时间、操作人，保留原业务状态和未收数量。
- 归档单不能继续发出、补货后发出、补录收回、撤回收回、删单或确认损耗。
- 原回收单仍可查询和正常结算付款；归档本身不改付款状态。
- 客户订单、补货记录不自动结案，需单独核对，不伪造业务完成。
- 已归档的待发出手工单不再预留可用库存，也不会被新批次自动合单；不能通过删除客户批次间接删除归档单。

## 安全部署顺序

**以下写入命令只能在完成备份、核对预览后执行。不要直接复制 apply 示例跳过前置步骤。**

本地代码完成不代表线上已更新；本功能不会在启动时自动归档。
既有 `deploy_aliyun_update.sh` 会同步整个项目并进行数据库兼容迁移，不应在备份前运行。
工作区若有其他尚未发布的改动，先检查发布范围，不要盲目全量同步。

1. 先确认服务器数据库连接与 `allen-shop.service` 使用的连接一致；脚本从项目根目录 `.env`
   及进程环境读取配置。不要将 `.env`、数据库密码或完整备份公开。
2. 在服务器安装／确认与数据库版本兼容的 `pg_dump` 和 `pg_restore`。
   `pg_dump --version`、`pg_restore --version` 只检查版本，不改数据。
3. 先上传新脚本及对应源码到受控发布目录；**不要重启服务或执行迁移**，先运行 backup。
   backup 子命令只读配置，不查询新归档字段，因此可在迁移前备份。
4. 暂停网页录单、机器人和其他写入任务，在短维护窗口执行备份、代码部署、迁移、预览和归档。
   只停主服务不一定能停掉单独运行的机器人；先确认实际部署方式。
5. 发布经过测试的代码和前端。启动时 `ensure_schema_compat()` 增加 nullable 归档字段，
   旧数据默认未归档；不会在启动时选择或归档任何订单。
6. 预览后核对单号、状态、数量、关联回收／付款信息；确认后才 apply。
7. 检查库存和付款状态不变、今天单据仍正常显示，再结束维护窗口。

### 备份（服务器终端）

在已上传脚本的项目根目录运行，备份文件放项目外，避免更新脚本误删：

```bash
cd /var/www/allen_shop
mkdir -p /root/allen-shop-backups
chmod 700 /root/allen-shop-backups
.venv/bin/python scripts/archive_production_orders.py backup --output /root/allen-shop-backups/before-archive-20261029.dump
```

成功时会生成 `.dump` 与同名 `.dump.json` 校验元数据；两者都要保留，并另存安全副本。
使用 PostgreSQL 自定义格式完整备份，并用 `pg_restore --list` 检查归档目录可读。
这不是完整恢复演练；如需恢复整个数据库，应先在独立数据库验证，不要直接覆盖线上库。
数据库密码通过子进程环境传递，不写进命令参数或 shell 历史。

如失败，先处理备份问题，**不要继续归档**。失败可能留下不完整文件，应换新文件名重试，
不得将其当作成功备份；脚本不会覆盖已存在文件。

### 只读预览（部署并迁移后）

```bash
.venv/bin/python scripts/archive_production_orders.py preview --before 2026-10-29 --output /root/allen-shop-backups/archive-preview-20261029.json
```

预览使用 PostgreSQL 只读、可重复读事务，不改业务数据。输出两类单据的数量、状态分布、单号、
业务日期以及完整确认摘要。JSON 包含原始单据、明细数量、实际配货数量、关联回收单及付款快照。
预览及备份文件权限为 600，请不要将原文件公开发送。

### 正式归档（核对预览后）

将 `预览输出的完整确认摘要` 替换成 preview 打印的 digest，不是批次号：

```bash
.venv/bin/python scripts/archive_production_orders.py apply \
  --plan /root/allen-shop-backups/archive-preview-20261029.json \
  --backup-file /root/allen-shop-backups/before-archive-20261029.dump \
  --confirm 预览输出的完整确认摘要 \
  --operator admin \
  --reason '历史业务结案，不再追踪；未收数量不视为实收，库存及付款信息不变'
```

- 必须提供同一数据库的已校验备份、原预览文件、正确的确认摘要、操作人和原因。
- 对相关业务表加事务级写锁（等待最多 10 秒），在一次事务中完成，失败则回滚。
- 预览后若有补录旧单、修改单据／数量／付款，拒绝执行，必须换文件名重新预览。
- 不自动纳入执行日之前的新单；截止日期始终取原预览文件。
- 重复执行同一批次会拒绝，不会重复影响业务。
- `.apply.json` 为操作记录；若报错或中断，应先核对数据库中 `archive_batch_id` 和日志，
  不要仅凭操作记录文件存在就认定提交成功，也不要随意删除记录文件后反复重试。

### 恢复这一次归档（不是恢复整个数据库）

如发现范围不对，保留所有文件并先停止写入、备份当前库，再由管理员执行：

```bash
.venv/bin/python scripts/archive_production_orders.py restore \
  --plan /root/allen-shop-backups/archive-preview-20261029.json \
  --backup-file /root/allen-shop-backups/before-archive-20261029.dump \
  --confirm 预览输出的完整确认摘要
```

只清除本批次的归档标记，不触碰库存、实收、付款或原状态。如果单据已不属于这个批次，
或归档后关联业务／付款发生变化，拒绝自动恢复，先人工对账。
